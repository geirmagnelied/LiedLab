# Tilgangsstyring — individuelle kontoar, kontor-administratorar og prosjekt-tilgang — spesifikasjon (27. okt. 2026) — IKKJE BYGD ENNO

Spesifisert i samtale med Geir Magne 26.–27. okt. 2026 (sikkerheitsgjennomgang
→ konkret krav), før implementering i Claude Code. **Dette er den største
enkelte endringa som er spesifisert i dette repoet** — den bytter heile
tilgangsmodellen frå «éin konto eig alt» til ekte, individuelle kontoar med
kontor-administratorar og separat prosjekt-tilgang, og rører i praksis RLS-
policyen på nesten alle tabellar i databasen. Les heile denne fila før du
rører autentisering, RLS eller `office_id`/`offices`-relatert kode.

## Kvifor (frå sikkerheitsgjennomgangen 26. okt.)

I dag er ALL data (`notes`, `cases`, `kanban_kort`, `framdrift_planar`,
`dtm_*`, `ks_*`, osv.) RLS-avgrensa strikt til `auth.uid() = user_id`.
Det finst ingen ekte deling mellom kontoar i databasen — kollegaer som skal
sjå dei samme prosjekta må i praksis dele éin og samme innlogging. Det gjev
null individuell sporbarheit, eitt stort felles feilpunkt (lekker det éine
passordet, er alt kundesensitivt materiale eksponert), og ingen måte å
stenge ute éin enkelt person. Geir Magne sitt krav etter denne gjennomgangen:

1. Kvart kontor skal kunne ha éin eller fleire **administratorar**.
2. Administratorar kan leggje inn **nye brukarar utan administrator-rettar**.
3. Kontoane må vere **individuelle** (éin konto per person).
4. Ein administrator skal **ikkje nødvendigvis** ha tilgang til all info i
   alle prosjekt — administrator-rolle og prosjekt-tilgang er to separate ting.

## Avklart med Geir Magne (27. okt.)

- **Tilgangsnivå i eit prosjekt**: berre medlem/ikkje-medlem. Står du på eit
  prosjekt, har du full tilgang til alt i det. Står du ikkje på det, ser du
  ingenting av det. Ingen lese-/rediger-rolle-forskjell innad i eit prosjekt
  (kan leggjast til seinare om behovet dukkar opp — sjå opne punkt).
- **Kven kan leggje folk til/fjerne frå eit prosjekt**: administratorar
  **OG** eksisterande medlemmar av det same prosjektet (t.d. ein
  prosjektleiar som ikkje har administrator-rolle for heile kontoret, men
  skal kunne invitere kollegaer inn i SINE prosjekt).
- **Migrering av eksisterande prosjekt**: berre Geir Magne sin noverande
  konto får tilgang automatisk. Alle andre sin tilgang til eksisterande
  prosjekt tildeles manuelt av han etterpå — ingenting breiere delt enn i
  dag på migreringsdagen.

## ⚠ Navnekollisjon å løyse: dagens `offices`-tabell er IKKJE det samme som det nye «kontor»-begrepet

Dagens `offices`-tabell (brukt i `TopBar.jsx` sin kontor-veljar,
`activeOfficeId`, fargetema `theme-private`/`theme-norconsult`) er ein
**personleg kategori-merkelapp** éin bruker lagar for å skilje t.d.
«Norconsult»- frå «Privat»-prosjekt i si EIGA liste — ikkje ein delt
organisasjon med fleire kontoar. Det nye «kontor»-begrepet i denne
spesifikasjonen er derimot ein **ekte, delt organisasjons-enhet** med
fleire medlemmar.

**Forslag**: behald dagens funksjon som den er (nyttig, ingen grunn til å
fjerne den), men gi den eit anna namn i databasen — t.d. `prosjekt_kategori`
i staden for `offices` — og la `offices`/«kontor» bli namnet på den nye,
ekte delte organisasjons-tabellen. Dette er ei rein omdøyping (tabellnamn +
tilhøyrande kode i `TopBar.jsx`/`useStore.js`), ingen funksjonell endring av
den eksisterande kategori-merkelappen. **Sei til om du ser det annleis.**

## Datamodell (ny)

```sql
-- Ekte, delt organisasjons-enhet ("kontor")
CREATE TABLE offices (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  namn        TEXT NOT NULL,
  created_by  UUID NOT NULL REFERENCES auth.users(id),
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Medlemskap + rolle i eit kontor
CREATE TABLE office_members (
  office_id   BIGINT NOT NULL REFERENCES offices(id) ON DELETE CASCADE,
  user_id     UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  rolle       TEXT NOT NULL DEFAULT 'medlem' CHECK (rolle IN ('administrator','medlem')),
  created_at  TIMESTAMPTZ DEFAULT NOW(),
  PRIMARY KEY (office_id, user_id)
);

-- Ventande invitasjonar (for e-postar som ikkje har konto enno, eller
-- som enno ikkje har logga inn etter at dei fikk ein)
CREATE TABLE office_invitations (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  office_id   BIGINT NOT NULL REFERENCES offices(id) ON DELETE CASCADE,
  epost       TEXT NOT NULL,
  rolle       TEXT NOT NULL DEFAULT 'medlem' CHECK (rolle IN ('administrator','medlem')),
  invitert_av UUID NOT NULL REFERENCES auth.users(id),
  status      TEXT NOT NULL DEFAULT 'ventar' CHECK (status IN ('ventar','innløyst')),
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- NØKKELTABELLEN: kven har tilgang til kva prosjekt
CREATE TABLE project_members (
  project_id   BIGINT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  user_id      UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  lagt_til_av  UUID REFERENCES auth.users(id),
  created_at   TIMESTAMPTZ DEFAULT NOW(),
  PRIMARY KEY (project_id, user_id)
);
```

`projects.office_id` endrar meining frå «personleg merkelapp» (sjå over) til
ein faktisk FK til den delte `offices`-tabellen.

## RLS-mønster: éin hjelpefunksjon, brukt alle stader

I staden for å skrive om alle policyar enkeltvis, lag éin funksjon og
referer til den i alle prosjekt-tilknytte tabellar:

```sql
CREATE FUNCTION kan_se_prosjekt(pid BIGINT) RETURNS BOOLEAN
LANGUAGE sql STABLE SECURITY DEFINER AS $$
  SELECT EXISTS (
    SELECT 1 FROM project_members WHERE project_id = pid AND user_id = auth.uid()
  );
$$;
```

Deretter byttes `USING (auth.uid() = user_id)` ut med
`USING (kan_se_prosjekt(project_id))` (og tilsvarande i `WITH CHECK`) på
**alle** prosjekt-tilknytte tabellar. Dette er lista over tabellar som må
migrerast (funne ved gjennomgang av alle `supabase-*.sql`-filer):

| Tabell | Fil |
|---|---|
| `notes` | `supabase-schema.sql` |
| `cases`, `case_comments`, `case_columns` | `supabase-cases.sql` |
| `kanban_kort`, `kanban_tavler` | `supabase-kanban.sql` |
| `framdrift_planar` | `supabase-framdrift.sql` |
| `dtm_dokumenter`, `dtm_versjonar`, `dtm_columns` | `supabase-dtm.sql` |
| `dtm_utsendingar`, `dtm_utsending_dokument` | `supabase-dtm-utsendingar.sql` |
| `ks_teikningar` | `supabase-ks-teikningar.sql` |
| `ks_kontroll_svar`, `kontaktar` | `supabase-ks-kontroll.sql` |
| `dtm_bilete`, `bilete_mobil_ko` | `supabase-bilete.sql` |
| `note_columns` | `supabase-notes-eigne-kolonnar.sql` |
| `sok_index` | `supabase-sok-index.sql` |
| `prosjekt_personell` | `supabase-personell.sql` |

`projects` sjølv får ein litt annan policy: `SELECT` via `kan_se_prosjekt(id)`,
men `INSERT` krev medlemskap i sjølve kontoret (`office_members`), og den
som opprettar prosjektet blir automatisk lagt til i `project_members`.

**Lagringsbøttene** (`bilete-mobil`, `dtm-resultatdokument`, m.fl.) må òg
migrerast: dagens filpath-mønster `<user_id>/<project_id>/<filnamn>` og
policy `(storage.foldername(name))[1] = auth.uid()::text` sjekkar i dag
berre at mappa høyrer til DIN EIGEN konto. Må bli ein sjekk av om
`project_id`-delen av stien er eit prosjekt du er medlem av, ikkje om
mappenamnet er din egen `user_id`.

**`kontor_kalender`** (personlege arbeidstidsinnstillingar) er IKKJE
prosjekt-tilknytt og trengs ingen endring — forblir `auth.uid() = user_id`.

## Administrasjonsrettar — eige spor, ikkje automatisk prosjekt-tilgang

`office_members.rolle = 'administrator'` gjev:
- Rett til å invitere nye brukarar til kontoret (`office_invitations`).
- Rett til å leggje til/fjerne personar frå **alle** prosjekt i kontoret
  (`project_members`) — same rett som eit prosjekt sine eigne medlemmar har
  for SINE prosjekt (avklart over).
- Sannsynlegvis: rett til å sjå kontorets personell-/fakturerings-oversikt
  på tvers av prosjekt (avklar ved bygging om dette skal krevje
  prosjekt-medlemskap eller ikkje).

Administrator-rolle gjev **IKKJE** automatisk ei rad i `project_members` —
ein administrator må leggjast til eit prosjekt eksplisitt, nøyaktig som
alle andre, for faktisk å sjå innhaldet i det. Dette er kjernen i kravet
om at administrator ikkje nødvendigvis har tilgang til all prosjektinfo.

## Invitasjonsflyt (unngår å måtte bruke ein privilegert service-role-nøkkel på klienten)

1. Administrator skriv inn e-post + rolle i eit nytt administrasjonspanel
   → rad i `office_invitations` (status `'ventar'`).
2. Den eksisterande, opne sjølvregistreringa (`Auth.jsx`) kan stå akkurat
   som i dag — ein ukjend som registrerer seg utan invitasjon får berre ein
   tom, isolert konto, akkurat som i dag (ingen ny risiko).
3. Ein ny trigger på `auth.users` (ved e-post-stadfesting) sjekkar om
   e-posten har ei ventande invitasjon i `office_invitations`. Finst den,
   opprettar triggeren automatisk raden i `office_members` og markerer
   invitasjonen `'innløyst'`. Same mønster (database-trigger som reagerer
   på `auth.users`) som `sok_index`-triggerane allereie brukar for andre
   tabellar i dette repoet — ingen ny arkitektur, berre eit nytt bruksområde.
4. **Merk**: kontobekreftinga (stadfestingslenke på e-post ved registrering)
   er ein standard Supabase-sikkerhetsmekanisme, uavhengig av — og ikkje i
   konflikt med — «unngå e-post»-kravet frå `claude/varslingssystem.md`.
   Det kravet gjaldt daglege hendingsvarsel (nye oppgåver/fristar), ikkje
   kontooppretting.

## Migrering av eksisterande data (éin gong, ved utrulling)

1. Opprett eitt `offices`-objekt for Geir Magne sitt kontor.
2. Legg Geir Magne til som `administrator` i `office_members`.
3. Sett `office_id` på alle eksisterande `projects`-rader til dette kontoret.
4. Legg Geir Magne til i `project_members` for **alle** sine eksisterande
   prosjekt (han skal ikkje miste tilgang til noko han har i dag).
5. Ingen andre kontoar/personar får noko automatisk — tildeles manuelt av
   han etterpå via det nye administrasjonspanelet, akkurat som avklart.

Varslingssystemet som allereie er spesifisert (bjølle-ikon, `varsler`-

## Omfang — vær bevisst på størrelsen før bygging starter

Dette er ikkje ei avgrensa feature — det endrar RLS-policyen på **12+
tabellar**, alle lagringsbøtte-policyar, og krev at praktisk talt alle
datahentings-funksjonar i `useStore.js` og modulfilene (som i dag filtrerer
på `.eq('user_id', userId)`) i staden filtrerer via prosjekt-medlemskap.
Anbefaling: bygg og test dette som eit eige, avgrensa steg (inkl. eit
testprosjekt med to-tre faktiske testkontoar) før noko annan ny
funksjonalitet legges oppå — ikkje som ein del av ein større leveranse.

## Opne punkt (ikkje avklart enno)

- Namnekollisjonen over (`offices` → `prosjekt_kategori`-omdøyping) —
  stadfest før bygging.
- Skal administrator kunne sjå kontorets personell-/fakturerings-oversikt
  på tvers av prosjekt, sjølv utan prosjekt-medlemskap i hvert enkelt?
- Lese- vs. rediger-rolle innad i eit prosjekt er medvite UTELATT no — kan
  leggjast til seinare (eit `rolle`-felt på `project_members` er enkelt å
  byggje på i etterkant, utan å endre grunnstrukturen).
- Kan ein administrator fjerne SEG SJØLV frå kontoret, eller frå det siste
  administratorsetet (må minst éin administrator alltid finnast)? Bør
  handteres ved bygging (t.d. hindre at siste administrator fjernar seg
  sjølv/nedgraderer seg).
