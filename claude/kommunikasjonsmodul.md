# Kommunikasjonsmodul — prosjektchat og eksterne samtalar — spesifikasjon (1. nov. 2026) — DEL 1 (PROSJEKTCHAT) BYGD 2. NOV. 2026, DEL 2 IKKJE BYGD

Spesifisert i samtale med Geir Magne 1. nov. 2026, før implementering i
Claude Code. To klart forskjellige behov, med to forskjellige
tilgangsmodellar — behandla som to separate delar av samme modul, ikkje
éin funksjon:

1. **Prosjektchat** — kommunikasjon mellom medlemmar av eit prosjekt.
2. **Ekstern/open kommunikasjon** — kommunikasjon med folk utanom
   kontoret, i open eller mindre grupper.

## Kvifor ikkje Slack/Mattermost (vurdert og avvist)

Vurdert mot Slack og Mattermost (sjå samtalen 1. nov.). Avvist i favør av
ein native modul, fordi:
- `kan_se_prosjekt()`-funksjonen og `project_members`-tabellen (frå
  `claude/tilgangsstyring.md`, no under bygging) er allereie nøyaktig den
  tilgangsstyringa ein prosjektchat trenger — ingen ny, parallell
  medlemsliste å halde synkronisert.
- Koden har allereie eit tilsvarande mønster: `case_comments`
  (`author`, `text`, `system`-flagg, `created_at`, knytt til `case_id`) —
  denne modulen generaliserer same mønster til prosjektnivå.
- Unngår ein ekstra tredjeparts-leverandør for kundesensitivt materiale,
  rett etter sikkerheitsgjennomgangen 26.–28. okt. — eitt system å sikre,
  ikkje to.
- Slack sin gratisversjon beholder berre 90 dagars historikk (i konflikt
  med «lagra i prosjektet» som eit varig arkiv), og tillèt ikkje å bli
  bygd inn i eit tredjeparts-vindauge. Mattermost kan sjølv-hostast, men
  det betyr ein ekstra serverapplikasjon DU må patche og sikre.

## Del 1 — Prosjektchat

**Filosofi (frå Geir Magne, viktig å ikkje bygge forbi):** appen skal
gjøres så effektiv på oppgåvehandtering at behovet for chatting i seg
sjølv blir begrensa. Dette er altså eit supplement, ikkje hovudverktøyet
— bygg **enklaste moglege versjon**, ikkje ein fullverdig chat-opplevelse.

- **v1: éin kronologisk strøm per prosjekt.** Ingen kanaler/tema enno.
- Datamodell, same mønster som `case_comments`:

```sql
CREATE TABLE prosjekt_meldingar (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  project_id  BIGINT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  user_id     UUID NOT NULL REFERENCES auth.users(id),
  tekst       TEXT NOT NULL,
  svar_til    BIGINT REFERENCES prosjekt_meldingar(id),  -- valfri trådsvar
  tema        TEXT,  -- ubrukt i v1-UI, men finst klar for fagvise chattar seinare
  system      BOOLEAN DEFAULT FALSE,  -- same flagg-idé som case_comments
  created_at  TIMESTAMPTZ DEFAULT NOW()
);
```

RLS: `select`/`insert` via `kan_se_prosjekt(project_id)` — identisk mønster
som `notes`/`projects` no bruker (sjå `supabase-sikkerheit-steg1.sql` steg
4–5). Ingen ny tilgangskode å skrive.

**Ingen redigering/sletting i v1** (same som `case_comments` i dag).
**`tema`-feltet** gjør det mogleg å legge til fagvise chattar seinare ved
bare å filtrere/gruppere på det — ingen migrering av eksisterande data
nødvendig den dagen.

Kommer praktisk talt gratis frå eksisterande/spesifisert infrastruktur:
- **Sanntid**: same Supabase Realtime-mønster som varsel-bjølla
  (`claude/varslingssystem.md`).
- **Søkbart**: ein `sok_index_prosjekt_meldingar()`-trigger, same mønster
  som `sok_index_notes()`/`sok_index_cases()` (sjå `supabase-sok-index.sql`).
- **Vedlegg**: same `Vedlegg`-bøtte som resten av appen.
- **Varsel** (seinare, ikkje v1): ein ny varseltype ved @nemning.

## Del 2 — Open/gruppechat, kun internt i kontoret

**Revidert 1. nov. 2026**: fyrste utkastet av denne delen lot eksterne
(folk utanom kontoret) delta via gjestekontoar. Geir Magne presiserte
etterpå at han **ikkje** ønsker at det skal vere mogleg å chatte med
eksterne frå appen i det heile. Del 2 er derfor avgrensa til
**kontorets egne medlemmar** — ingen gjestekontoar, ingen invitasjon av
eksterne, ingen eige forenkla grensesnitt for folk utanfor kontoret.

Behovet som blir stående: open kommunikasjon som ikkje er knytt til ett
enkelt prosjekt (kontor-breitt), eller mindre interne grupper tvers av
prosjekt — men alltid avgrensa til dei som allereie er
`office_members` for det kontoret.

### Datamodell

```sql
-- Ein samtale: open for heile kontoret, ELLER ei avgrensa, intern gruppe
CREATE TABLE samtalar (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  office_id   BIGINT NOT NULL REFERENCES offices(id) ON DELETE CASCADE,
  namn        TEXT NOT NULL,
  er_open     BOOLEAN NOT NULL DEFAULT false, -- true = alle i dette kontoret, false = kun eksplisitt lista deltakarar
  created_by  UUID NOT NULL REFERENCES auth.users(id),
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Eksplisitt deltakarliste for AVGRENSA grupper (kun relevant når
-- er_open = false). Alle som legges til MÅ vere office_members for
-- samme kontor — handheva av kan_leggast_til_samtale() under.
CREATE TABLE samtale_deltakarar (
  samtale_id   BIGINT NOT NULL REFERENCES samtalar(id) ON DELETE CASCADE,
  user_id      UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  lagt_til_av  UUID REFERENCES auth.users(id),
  created_at   TIMESTAMPTZ DEFAULT NOW(),
  PRIMARY KEY (samtale_id, user_id)
);

CREATE TABLE samtale_meldingar (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  samtale_id  BIGINT NOT NULL REFERENCES samtalar(id) ON DELETE CASCADE,
  user_id     UUID NOT NULL REFERENCES auth.users(id),
  tekst       TEXT NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT NOW()
);
```

Ingen `samtale_invitasjonar`-tabell, ingen e-postbasert invitasjon — å
legge nogen til ei avgrensa samtale er ei vanlig «vel frå lista over
kontorets medlemmar»-handling, akkurat som å legge ein kollega til eit
prosjekt. Ingen ny innloggingsmekanisme, ingen gjestekontoar.

### RLS-logikk

`samtalar`/`samtale_meldingar` er synlege for ein bruker dersom:
```
(er_open = true AND is_office_member(office_id))
OR
EXISTS (SELECT 1 FROM samtale_deltakarar WHERE samtale_id = ... AND user_id = auth.uid())
```

`samtale_deltakarar`-innsetting krev ein tilsvarande sjekk som
`project_members` sin `kan_leggast_til(pid, uid)`: ein ny funksjon
`kan_leggast_til_samtale(sid, uid)` som nektar innsetting dersom `uid`
ikkje er aktiv `office_member` av samtalens kontor. Dette er den
konkrete, databasehandheva garantien mot at nogen utanfor kontoret kan
leggast til — ikkje bare eit UI-val som kan hoppast over.

Ingen eige forenkla grensesnitt nødvendig — alle som kan logge inn og
sjå noko i det heile, er allereie fulle kontormedlemmar.

## Opne punkt (ikkje avklart enno)

- Skal ein administrator for kontoret kunne sjå/administrere ALLE
  avgrensa samtalegrupper, eller bare dei dei sjølv er lagt til i?
  Foreslår: administrator kan sjå lista over samtalar (namn/deltakarar),
  men ikkje innholdet, med mindre dei er lagt til som deltakar — same
  prinsipp som prosjekt-tilgang.
- Skal `prosjekt_meldingar` sitt `tema`-felt få eit konkret UI (filtrering,
  fane-val) når fagvise chattar faktisk blir bygd, eller held det med éin
  flat liste filtrert på klikk?
