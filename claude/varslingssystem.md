# Varslingssystem — spesifikasjon (26. okt. 2026) — IKKJE BYGD ENNO

Spesifisert i samtale med Geir Magne 26. okt. 2026, før implementering i
Claude Code. Mål: varsle folk internt i appen når dei blir satt som
ansvarleg for ei ny oppgåve (kanban), sak, eller frist i eit prosjekt —
**utan e-post**.

## Bakgrunn — status i dag (funne ved gjennomgang av koden)

- Det finst **ingen** eksisterande varslings-/push-infrastruktur: ingen
  bruk av Supabase Realtime (`postgres_changes`), ingen service worker,
  ingen Web Push, ingen bruk av Electron/nettlesaren sin innebygde
  `Notification()`-API.
- Det finst derimot ein brukbar **identitets-grunnmur**: ekte kontoar via
  `auth.users`, med `brukar_profil` (profil) og `prosjekt_personell`
  (kven som jobbar på kva prosjekt, `user_id`-kopla) — same kjelde som
  Framdrift-modulen bruker til personell i dag.
- **Kritisk hinder**: feltet «ansvarleg» er i dag lagra som **fritekst**
  (`ansvarleg TEXT`) på kanban-kort (`supabase-kanban.sql`), saker
  (`supabase-cases.sql`) og oppgåver inni notat (`task.ansvarleg`, inne i
  `notes.tasks`-JSONB). Ingen av desse er kopla til ein faktisk konto —
  eit varsel kan ikkje rutast til «rett person» utan dette er løyst først.

## Steg 0 (forutsetning) — Kople «ansvarleg» til ein ekte konto

- Gjer «ansvarleg»-feltet til ei nedtrekksliste bygd på kontorets
  personell-liste (same kjelde som Framdrift-modulen sitt personellvalg),
  i staden for eit fritekstfelt.
- Lagre **begge**: det eksisterande visningsnamnet (`ansvarleg`, for
  bakoverkompatibilitet og visning) OG eit nytt `ansvarleg_user_id`
  (FK → `auth.users`), på alle tre stadar (kanban-kort, saker, task-objekt
  i notat-JSONB).
- Eksisterande data: autokople der namnet matchar ein kjend konto eksakt.
  Resten vises med ein liten indikator («ikkje kopla til konto») —
  varsel kan ikkje sendast for desse før dei er kopla manuelt éin gong.

## Varsel ved tildeling — éin gong, ingen påminning

Avklart med Geir Magne: **eitt varsel når ansvarleg blir satt** (ved
oppretting, eller ved ny-tildeling/endring av ansvarleg) er nok. Ingen
separat påminningsjobb nær fristen.

## Datamodell — ny tabell `varsler`

```sql
CREATE TABLE varsler (
  id                BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  mottakar_user_id  UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  type              TEXT NOT NULL, -- 'ny_oppgave' | 'ny_sak' | 'ny_frist'
  tittel            TEXT NOT NULL,
  prosjekt_id       BIGINT REFERENCES projects(id) ON DELETE CASCADE,
  referanse         JSONB NOT NULL DEFAULT '{}', -- { kilde:'kanban'|'sak'|'notat', id, note_id?, task_id? }
  lest              BOOLEAN NOT NULL DEFAULT false,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_varsler_mottakar ON varsler(mottakar_user_id, lest, created_at DESC);
```

RLS: `SELECT`/`UPDATE` (merk som lest) kun der `auth.uid() = mottakar_user_id`.
**Ingen direkte `INSERT`-policy for klienten** — ein bruker kan ikkje
lovleg skrive ein varsel-rad for ein ANNAN bruker under vanlege RLS-regler.
Oppretting skjer i staden via ein Postgres-funksjon:

```sql
CREATE FUNCTION opprett_varsel(mottakar UUID, varsel_type TEXT, tittel TEXT, prosjekt BIGINT, ref JSONB)
RETURNS void LANGUAGE sql SECURITY DEFINER AS $$
  INSERT INTO varsler (mottakar_user_id, type, tittel, prosjekt_id, referanse)
  VALUES (mottakar, varsel_type, tittel, prosjekt, ref);
$$;
```

Kalla frå appkoden (`supabase.rpc('opprett_varsel', {...})`) rett etter at
`ansvarleg_user_id` blir satt/endra — i `addTask`/`updateTask` (notat-
oppgåver), i kanban-koden (`kanbanLogikk.js`/`KanbanKortModal.jsx`), og i
`SakerModule.jsx`. Dette held varsel-logikken samla i appkoden i staden
for spreidd i databasetriggerar — enklare å følge og vedlikehalde i dette
kodebasen, der alle skriveoperasjonar allereie går gjennom dedikerte
funksjonar i `useStore.js`/modulfilene.

## UI — bjølle-ikon med sanntidsliste

- **Plassering**: ved brukarmenyen oppe til høgre (same plass vi nettopp
  stadfesta/flytta brukarmenyen til i `claude/mobil-grensesnitt.md`) —
  både skrivebord og mobil.
- **Talmerke** viser antal uleste. Klikk opnar ei nedtrekksliste med dei
  siste varsla (nyeste øverst), éi linje per hending: type-ikon + kort
  tekst («Ny oppgåve: … — Prosjekt X», «Ny frist: … — Prosjekt X») +
  kor lenge sidan. Klikk på ei linje navigerer rett til kortet/saka/
  notatet (via `referanse`-feltet) og merker varselet som lest.
- **Sanntid**: Supabase Realtime-subscription
  (`supabase.channel(...).on('postgres_changes', { event:'INSERT', table:'varsler', filter:'mottakar_user_id=eq.<meg>' }, ...)`)
  — badge og liste oppdaterer seg momentant utan sideoppdatering.

## Framtidige tillegg (ikkje no, men bygd for å kunne leggast på utan omskriving)

- **Skrivebord, gratis tillegg**: Electron/Chromium sin innebygde
  `Notification()`-API kan vise ein native OS-boks av same realtime-
  strøm, utan ny infrastruktur — berre eit lite lag oppå den
  eksisterande subscriptionen.
- **Varsel når appen er heilt lukka** (ikkje avklart som eit krav no,
  sjå samtalen 24.–26. okt.): om det seinare blir viktig, legg det på
  SOM ET TILLEGG oppå den same `varsler`-tabellen — ein Supabase
  database-webhook som trigger ved ny rad, og sender Web Push (krev
  service worker + VAPID-nøklar + ein eigen abonnements-tabell per
  enhet). Ikkje eit parallelt system, berre ein ekstra lytter.
